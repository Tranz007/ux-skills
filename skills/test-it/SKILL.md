# Test It

Validate the uncertainty that can change the decision.

## Start with the decision

Inspect the problem frame, evidence, assumptions, design, flow, and consequences. Identify what the team is uncertain about and which uncertainty actually matters.

Do not default to a usability test when analytics, support data, an engineering spike, accessibility testing, a content check, or another method answers the question better.

## Form testable questions

Translate vague goals such as "validate the design" into observable questions.

Examples:

- Can users recognize which recovery option applies to them?
- Do users recover after an expired verification code without external help?
- Does the new pattern work with keyboard and expected screen-reader behavior?
- Does the proposed component composition handle the required data volume?

Avoid framing that presumes the preferred design succeeds.

## Choose the smallest useful method

For each important uncertainty, state:

- what needs to be learned;
- the best evidence source or method;
- who or what needs to be included;
- what observation would change the decision;
- what can remain unknown for now.

## Protect research integrity

Do not fabricate participants, findings, confidence, or statistical meaning. Avoid leading tasks and questions. Distinguish exploratory learning from evaluative testing.

## Output

Prefer a focused plan that a team could actually run. If there is nothing material to validate, say so rather than creating research theater.

## Examples

- "How should we test this before engineering builds it?"
- "What would prove this assumption wrong?"
- "We can't test everything. What matters most?"
